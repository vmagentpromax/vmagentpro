# 场景 F 调度策略对比结果

更新时间：2026-11-02。四组普通 FCFS、五组 Backfill，以及 SpotGPU + FCFS 均已在本机使用性能优化后的 VMAgentPro 调度器运行。FCFS 专用 HP 候选索引修正只影响 SpotGPU + FCFS 的抢占路径，不改变其余九组的调度行为；四组普通 FCFS 的指标在本文展示精度下复现原结果。

## 1. 实验问题与范围

本实验比较异构、高负载场景中节点放置策略和队列策略的影响，重点观察：

1. 在 FCFS 严格队首调度下，不同放置策略造成的资源碎片和队首阻塞；
2. Backfill 是否能让队首暂时无法放置时的后续可运行任务先启动；
3. SpotGPU 在 HP GPU 任务到达时抢占 LP spot GPU 任务所带来的资源利用率收益和抢占损耗。

本实验是仿真器中的 CPU/GPU 资源预留模拟，不是在真实服务器上执行模型推理或训练，也没有运行在超算平台上。

## 4. 指标口径和解释

- **提供负载（offered ratio）**：把输入任务请求资源在理想到达/运行区间内积分，除以资源池容量和 691,200 秒测量窗。GPU、CPU 提供负载分别为 96.11%、143.89%，所有策略相同。
- **资源预留率（reserved ratio）**：对仿真账本中的实际 GPU/CPU 分配随时间积分，再除以资源池容量和统计时长。排空结果使用完整测量窗口；被时间上限截断的 FCFS 结果使用已覆盖测量窗口。固定 CPU 背景为 0。
- **等待时间**：任务实际开始时间减去提交时间，并按已开始任务统计。P95 使用最近秩（nearest-rank）计算。
- **峰值队列**：任一仿真时刻等待任务数的最大值。
- **峰值 GPU/CPU 预留**：全池同时处于分配状态的 GPU 数和 CPU 核数峰值；不是平均值或预留率。
- **模拟天数**：结束时仿真时间除以 86,400。4,000,000 秒上限约为 46.30 个仿真日。
- **墙钟秒**：本机实际运行耗时，受进程和系统负载影响。它不是仿真时间，也不是策略质量指标。
- **资源指标边界**：GPU 预留不等于 GPU SM 利用率或计算吞吐；CPU 预留不等于 CPU 指令执行利用率。仿真器只模拟 CPU/GPU 资源占用账本。

## 5. 结果分析

### 5.1 FCFS：放置策略决定队首阻塞与碎片

Best Fit 的平均等待最低（177.97 小时，P95 278.72 小时），First Fit 接近（187.11 小时）。Worst Fit 在 4,000,000 秒上限处还有 6 个任务未完成，GPU/CPU 预留率仅 12.8%/11.1%；Random 有 5 个任务未完成。Worst Fit 的结果体现严重队首阻塞与碎片化，不能称为数学意义上的永久死锁。

### 5.2 Backfill：可放置任务越过阻塞任务

五种 Backfill 策略均排空全部任务。FCFS 下 Worst Fit 的 6 个未完成任务在 Backfill 下全部完成；平均等待从 428.16 小时降至 48.18 小时。五个策略中，Worst Fit 的平均等待最低（48.18 小时），Random 为 48.57 小时，Best Fit 为 58.21 小时，First Fit 为 58.96 小时。该场景中平均等待与 GPU 预留率不完全同向。

### 5.3 异构 GPU 型号池不可互换

XPU-A 提供负载约为其 GPU 容量的 104.1%，H20 约为 80.2%。Worst Fit + Backfill 的 XPU-A GPU 预留率为 91.1%，H20 为 47.1%；只看全池平均会隐藏机型池差异。

### 5.4 SpotGPU：预留率提高，但不保证 HP 等待更短

SpotGPU + Backfill 的全池 GPU 预留率为 86.7%，XPU-A GPU 预留率为 98.9%；代价是 226 次抢占、212 个被抢占任务和约 39.14 GPU·小时的浪费。其总体平均等待 65.80 小时，HP 平均等待 67.15 小时，LP 为 83.57 小时。新增的 SpotGPU + FCFS 全池 GPU 预留率为 81.3%，发生 232 次抢占，浪费约 7.97 GPU·小时；平均等待为 227.49 小时，明显受 FCFS 队首阻塞影响。两种组合都是普通可运行任务优先、队列阻塞时才尝试 HP 抢占；FCFS 下被选中的 HP 可能越过队首，因此不能称为严格 HP 优先队列或绝对严格 FCFS。

### 5.5 CPU 是持续紧约束

输入 CPU 提供负载约为容量的 143.9%，五组 Backfill CPU 预留率均接近 100%。GPU 预留率提高并不说明 CPU 瓶颈已消除，也不能据此推断实际 GPU 计算吞吐提高。

## 6. 运行过程、结果文件与复现

1. 使用同一份 `sim_inputs/nodes.csv` 和 `sim_inputs/jobs_F.csv`，核对 30 节点、119,495 个任务及型号约束。
2. 采用 `fast` 时钟、seed 42、测量窗 691,200 秒、最大仿真时间 4,000,000 秒、CPU 背景 0。SpotGPU 显式设置 3,600 秒 checkpoint。
3. 在优化后的代码版本上运行四组普通 FCFS（First Fit、Best Fit、Worst Fit、Random）、五组 Backfill（First Fit、Best Fit、Worst Fit、Random、SpotGPU），以及 SpotGPU + FCFS。
4. 四组普通 FCFS 复跑结果写回 `outputs/F-<policy>-fcfs/`；Backfill 输出位于 `outputs/F-<policy>-backfill/`；SpotGPU + FCFS 位于 `outputs/F-spotgpu-fcfs/`。各目录均保存汇总、任务明细、事件、资源历史、最终节点状态和运行清单。
5. 早期 SpotGPU + FCFS 试跑暴露出 HP 抢占候选索引仅在 Backfill 初始化的缺陷。已将 HP 候选索引改为与队列策略无关，增加 FCFS 抢占回归测试，修复后重新运行并以最终结果覆盖该次试跑。
6. 核对各任务 CSV 明细为 119,495 行，并检查策略、队列、seed 和汇总计数。五组 Backfill 与 SpotGPU + FCFS 均 `drained`；普通 FCFS Worst Fit、Random 到达时间上限，分别有 6、5 个未完成任务。
7. 调度器回归测试：16 项通过，覆盖同需求任务的 Backfill 次序、SpotGPU 在 FCFS/Backfill 队列的抢占与检查点恢复、资源账本、截止时间、同刻事件和输入校验。

场景文件：

- 节点：`sim_inputs/nodes.csv`
- 任务：`sim_inputs/jobs_F.csv`
- FCFS：`outputs/F-first_fit-fcfs/`、`outputs/F-best_fit-fcfs/`、`outputs/F-worst_fit-fcfs/`、`outputs/F-random-fcfs/`
- SpotGPU + FCFS：`outputs/F-spotgpu-fcfs/`
- Backfill：`outputs/F-first_fit-backfill/`、`outputs/F-best_fit-backfill/`、`outputs/F-worst_fit-backfill/`、`outputs/F-random-backfill/`、`outputs/F-spotgpu-backfill/`

PowerShell 复现示例（从 `vmagentpro` 仓库根目录执行；修改 `$queue` 和 `$policy` 可运行其他组合）：

```powershell
$policy = 'first_fit'
$queue = 'backfill'
python -m vmagent.gpu.run `
  --nodes 'D:\vmagent_scenarios_hetero_8d\sim_inputs\nodes.csv' `
  --tasks 'D:\vmagent_scenarios_hetero_8d\sim_inputs\jobs_F.csv' `
  --policy $policy `
  --clock fast `
  --queue-policy $queue `
  --measurement-seconds 691200 `
  --max-sim-time 4000000 `
  --cpu-background-fraction 0 `
  --checkpoint-interval 3600 `
  --seed 42 `
  --output "D:\vmagent_scenarios_hetero_8d\outputs\F-$policy-$queue"
```

# 原 20 台 H20：两个连续窗口与 FirstFit / BestFit 跑通说明

> 历史方案，已被本轮“小时请求饱和度优先”的重建流程替代。这里的 relative_low / relative_high、6 小时预热和数千任务输入保留用于追溯，不能作为新流程的自然高低负载场景。新方法见 [request_load_scenes/METHOD.md](../request_load_scenes/METHOD.md)，新构建结果见 [request_load_scenes/README.md](../request_load_scenes/README.md)。

## 1. 已完成的内容

沿用 `docs/server_selection/servers_20_H20.csv` 的原 20 台 H20，容量始终为 **160 GPU、3,840 CPU 核**。两组都保留所选节点在连续预热段、正式测量段出现的全部唯一 Pod，包括 CPU-only Pod；没有为了凑比例删除任务。

- **相对低 `relative_low`**：正式窗口 day167/00～23；源 GPU 资源时间占比 **93.3671%**。24,171 个 Pod，其中预热任务 4,478 个、正式窗口新增 19,693 个，GPU 正请求任务 543 个。
- **相对高 `relative_high`**：正式窗口 day110/00～23；源 GPU 资源时间占比 **99.2957%**。4,307 个 Pod，其中预热任务 613 个、正式窗口新增 3,694 个，GPU 正请求任务 638 个。

这里的“低”仅指两者相对较低，**不是低于 40% 的绝对低负载**。原三天 GPU 占比为 97.18%～99.80%；对其他日期的每日 12 时进行粗查后，进一步核验 day167 的完整窗口，未声称穷举全部日期的每一小时。两个场景适合当前跑通验证，不能据此得出跨负载的一般性能结论。

源占比使用 `Σused_gpu_hours / (160×24小时)`，不是 SM 利用率，也没有将每条小时观测都当作完整一小时的实际 GPU 使用。节点配置已核验：较低窗口含预热、后视观察的 54 小时逐小时核验；较高窗口在此前 109～111 天的 72 小时核验范围内。

## 2. 到达、执行时间与预热

每组都使用 **6 小时连续前置预热＋24 小时正式窗口**，另读正式结束后 24 小时，仅辅助估计已有任务何时结束，不引入这段时间的新任务。

```text
相对低：day166/18 开始预热 → day167/00 正式测量 → day168/00 停止新到达
相对高：day109/18 开始预热 → day110/00 正式测量 → day111/00 停止新到达
```

时间重建规则统一如下：

1. 按 `pod_id` 去重，同一序列中一行一个任务。首次出现小时视为估计到达小时，同小时按 `pod_id` 排序，不添加随机间隔。
2. GPU、CPU 取该 Pod 首次观测同一行的真实配对请求，在本次静态任务模型中保持不变。源请求发生变化的任务没有被删除：较低组 312 个、较高组 285 个；变化保存在原始小时记录中，本轮没有模拟运行中的资源调整。
3. 执行跨度估计为“末次观测小时结束－首次观测小时开始”。较高组有 10 个 Pod 存在观测空缺，本轮按连续跨度近似；较低组无空缺。超过后视观察末端的任务属于右截断估计，分别有 359、388 个，不能认为掌握了真实完成时刻。
4. 已在预热起点存在的任务在预热起点进入模拟器，它们的预热前历史和精确剩余时间未知。预热开始为空节点池，真实前置任务经过调度形成初始占用和队列；不按原宿主强行预装可能不满足容量的小时请求集合。

公开数据只有小时观测，所以这里是**真实任务与真实请求、估计时间的连续回放**；`service_sec` 不是精确历史执行时长。未使用随机时长，也未将不确定的 execution-summary 匹配直接当作精确实例。

统一时间压缩系数 **K=900**，原始 1 小时对应回放 4 秒：

```text
submit_time_sec = (首见小时 - 预热起始小时) × 3600 / 900
service_sec = (末见小时 - 首见小时 + 1) × 3600 / 900
预热区间：[0,24) 秒；正式资源测量区间：[24,120) 秒
```

到达、服务时长与测量窗口使用同一系数，保持该重建模型的需求时间比例。两组重建后的 GPU offered load 分别为 **106.1677%、119.0771%**，CPU 为 **122.8168%、106.4564%**，不等于源 GPU 使用占比。请求压力超过 100% 时任务排队，不允许超分配。

正式开始时保留预热形成的运行任务和队列，资源统计排除前 24 秒；尚未证明统计稳态。停止新任务后继续排空，服务时长从实际调度成功时开始计时。默认 `fast` 不等待墙钟，可在一分钟内完成单轮；`realtime` 排空可能超过两分钟，不能把“120秒输入窗口”误解为“120秒内一定全部完成”。

## 3. 直接运行

PowerShell 在仓库根目录执行。运行器只依赖 Python 标准库；重建数据另需 pandas、numpy、pyarrow。

```powershell
cd 'D:\一般文件\VMAgent'

# 两组 × FirstFit、BestFit，共4轮；默认快速事件模式
python docs/server_selection/run_two_gpu_scenes.py

# 只运行一轮
python docs/server_selection/run_two_gpu_scenes.py --scene relative_low --policy best_fit
python docs/server_selection/run_two_gpu_scenes.py --scene relative_high --policy first_fit

# 需要观看较快实时回放时：speed=2将回放墙钟再加快2倍
python docs/server_selection/run_two_gpu_scenes.py --scene relative_high --policy first_fit --clock realtime --speed 2
```

FirstFit 选第一个同时满足 GPU/CPU 容量的节点；BestFit 在可放节点中最小化 `(剩余GPU/节点GPU容量)+(剩余CPU/节点CPU容量)`，相同时按节点顺序选。两者均用 backfill 队列、相同输入和预热规则，其他配置相同。

## 4. 本次实测结果

- 较低组 FirstFit：24,171/24,171 完成，约 **36.06秒**；正式窗口 GPU 预留 **88.2581%**，正式新增任务平均等待 **16.5356秒**。
- 较低组 BestFit：24,171/24,171 完成，约 **37.34秒**；GPU 预留 **88.2841%**，平均等待 **16.5976秒**。
- 较高组 FirstFit：4,307/4,307 完成，约 **5.72秒**；GPU 预留 **97.5927%**，平均等待 **5.9924秒**。
- 较高组 BestFit：4,307/4,307 完成，约 **5.83秒**；GPU 预留 **97.5406%**，平均等待 **5.7336秒**。

以上墙钟时间与机器有关，等待时间为压缩后的模拟秒。四轮均 **0 拒绝、0 未完成、节点资源完全归还**。较低组 CPU 预留达到 100%，因此 GPU 源负载较低不代表任务等待更短。正式新增任务指标见 `measurement_cohort_metrics.json`；通用 `summary.json` 的等待指标包括预热任务，不能混用。

预热核验文件 `warmup_audit.json` 给出正式到达前的真实模拟状态。例如较低组 FirstFit 在第24秒有 568 个运行任务、630 个等待任务，已完成 3,280 个预热任务；正式开始没有重置为空集群。

## 5. 数据、结果与网页

- 输入：本目录 `relative_low/tasks.json`、`relative_high/tasks.json`，可直接用于运行器。对应 `tasks.csv` 保留详细构造标记；`source_observations.parquet` 保留原始请求变化及来源。
- 结果：仓库 `outputs/gpu/two_scenes/<场景>/<策略>/`，包含汇总、任务明细、事件日志、资源曲线、节点最终状态、预热核验、正式任务指标及输入配置。
- 四轮汇总：`outputs/gpu/two_scenes/comparison.csv` 和 `.json`。
- 两个序列各自没有重复 Pod；跨两个独立实验存在 207 个共同真实 ID，主要是持久任务。为保留完整连续数据，没有改名或剔除；**不满足跨场景所有 ID 完全互斥的旧约束**。

启动当前版本网页：

```powershell
python -m vmagent.gpu.dashboard --port 8766
```

打开 <http://127.0.0.1:8766/>，服务器可沿用内置20台；上传本目录某组 `tasks.json`，选择 FirstFit/BestFit 和“快速模式”，点击开始。JSON 上传后自动填入测量开始24秒、长度96秒，前24秒为预热。**优先上传 JSON**；CSV不携带测量窗口元数据。大量任务时页面只显示筛选后的前200条，完整任务通过下载查看。若旧服务已启动，必须重启或使用新端口才能加载本次预热支持。

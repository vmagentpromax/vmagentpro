# 场景 B：固定原 20 台 Server 的连续 72 小时核验

## 结论

按用户确认的要求，保留原来 20 台 Server 在第 109～111 天全部 72 个小时内的真实 Pod，不挑选任务子集。连续观测已导出，但**这组固定数据不满足 B 的 GPU 90%、CPU 30% 目标**，也不满足 GPU 80%～95%、CPU 不超过 40% 的高低区间。原单小时 B 文件保留作为旧版本，本目录不把不达标的数据标记为合格场景 B。

## 窗口、来源与去重

- 窗口：day109/hour00 至 day111/hour23，时长 72 小时。
- Server：完全沿用 `docs/server_selection/servers_20_H20.csv`，共 20 台，每台 8 GPU、192 CPU 核，总计 160 GPU、3,840 CPU 核。
- 从原始 Pod 小时 Parquet 按这 20 个 `server_id` 直接读取全部记录；没有因请求变化、与旧场景重复、观测中断而删除 Pod，也没有修改请求或补入任务。
- 共 56,154 条 Pod 小时观测、19,774 个唯一 `pod_id`。其中 1,101 个有 GPU 正请求，型号标签全部为 H20；其余为 CPU-only Pod。
- `unique_pods.csv`、`unique_gpu_pods.csv` 按 `pod_id` 一行一个任务。小时观测文件中同一 Pod 会跨小时出现，这是计算时间积分所需的记录，不表示重复提交任务。

## 执行时间估计与公式

小时表没有准确运行起止时间。本次按用户选择，以每个 Pod 实际出现的不同小时数作为窗口内执行时长的代理：

```text
H_i = Pod i 在固定节点池中实际被观测到的小时集合
估计窗口内执行时间 t_i = |H_i| × 1小时
```

有间断时只累计实际观测小时，不用“末见−首见+1”填补空缺；窗口开始已存在的 Pod 按窗口内观测计入。共有 12 个 Pod 的观测存在空缺。该估计没有恢复秒级到达顺序。

需求不变时，用户指定的公式为：

```text
GPU负载 = [Σ_i (GPU需求_i × t_i)] / (160 × 72小时)
CPU负载 = [Σ_i (CPU需求_i × t_i)] / (3,840 × 72小时)
```

括号中的整个容量乘窗口时长是分母。小时与小时应使用相同时间单位。

全部 Pod 中有 777 个观测到请求变化，其中 GPU Pod 有 4 个。为保留全部真实记录，请求变化的任务按每小时原始请求分段积分，不能随意选取一个固定请求：

```text
GPU估计资源时间 = Σ_i Σ_{h∈H_i} GPU需求_{i,h} × 1小时
CPU估计资源时间 = Σ_i Σ_{h∈H_i} CPU需求_{i,h} × 1小时
```

需求不变时，分段公式与需求乘执行时间相同。去重清单中，请求发生变化的任务将对应固定请求字段留空，原始变化值保留在小时观测文件中；每个任务的积分值直接给出在 `gpu_hours_proxy`、`cpu_core_hours_proxy`。

## 计算结果

B 的精确目标：

```text
GPU：160 × 72 × 90% = 10,368 GPU·小时
CPU：3,840 × 72 × 30% = 82,944 CPU核·小时
```

按全部真实 Pod 计算：

```text
GPU：12,882.4 / 11,520 × 100% = 111.8264%
CPU：289,223 / 276,480 × 100% = 104.6090%
```

即使 CPU 分子仅统计有 GPU 请求的 1,101 个 Pod，CPU 仍为：

```text
CPU：210,246.25 / 276,480 × 100% = 76.0439%
```

CPU-only Pod 的部分为 78,976.75 CPU核·小时。全部 Pod 与 GPU Pod 两种口径均未达到 B。

这些数值是**按小时出现次数累计的请求暴露量估计**，不是实测 GPU/CPU 利用率。一个小时内先后出现的任务可能都被记录；把它们各计为完整一小时会累计到超过节点容量，故超过 100% 不能直接解释为物理资源超载。执行汇总虽然另有 `duration_hours`，但没有足够的起止时刻及执行实例关联来精确裁剪本窗口，不能把窗口外完整时长直接加进来。

## 文件与使用边界

- `unique_gpu_pods.csv`：1,101 个唯一 GPU Pod，含原始需求（恒定时）、观测时长代理、来源 Server、观测小时索引、资源时间积分。
- `unique_pods.csv`：19,774 个唯一 Pod，包含 CPU-only Pod。
- `all_pod_hourly_observations.csv` / `.parquet`：原始字段和窗口小时索引，共 56,154 行，用于分段积分及追溯。
- `hourly_load_proxy.csv`：连续 72 个小时的请求总量和容量比例。
- `audit.json`：数值结果、节点 ID、请求变化统计与旧场景 ID 交集。
- 复现脚本：`docs/server_selection/audit_scene_B_continuous.py`，运行 `python docs/server_selection/audit_scene_B_continuous.py`。

保留全部任务还会与旧 A/C/D/E 分别重合 1/2/2/3 个 ID，具体 ID 见审计文件。因此当前同时保持“本次连续窗口全部任务”与“五场景全局 ID 无交集”也不可行；本次遵循保留全部任务的最新要求，没有静默剔除。

本目录没有生成模拟器要求的精确 `submit_time_sec`、`service_sec`，不能作为已有界面的完整仿真任务文件直接上传。若需在原 20 台 Server、固定 72 小时、全部真实任务不删减的条件下达到 B，当前数据不能支持；需改变窗口或实验约束，不能通过改写真实时长或删除任务强行达标。

# 小时请求负载优先的自然场景构建方法

本轮固定使用 `servers_20_H20.csv` 中原有 20 台节点，仿真容量为 160 GPU、3,840 CPU 核。严格保留自然窗口约束；没有合格低负载窗口时，报告缺失，不通过调慢到达、抽取小任务子集、换节点或改分母来构造替代。

## 分类先于执行时间

扫描 `asi_opensource_pod_hourly` 所有可访问的 day/hour 分区，只取原 20 台节点上的观测。每个小时先去除完全相同的重复行；同一 Pod 在同小时存在冲突记录时中止，而不任意挑一行。

- GPU 请求饱和度：当小时 `Σgpu_request / 160`。
- CPU 请求饱和度：当小时 `Σcpu_request_cores / 3840`，包括这些节点上的 CPU-only Pod。
- 高负载候选：连续窗口平均 GPU 请求饱和度 ≥ 0.80，且 CPU ≥ 0.60。
- 低负载候选：连续窗口平均 GPU 请求饱和度 ≤ 0.35，且 CPU ≤ 0.35。
- 穷举全部整数长度 6～24 小时的连续窗口，GPU 正请求的唯一 Pod 数必须在 50～150。

分子与分母对应同一组 20 台节点，不能把整个原始大集群的请求量除以这 20 台的容量。小时内观测过的 Pod 请求之和可以超过容量：它是小时观测请求强度，不证明这些 Pod 同时运行，也不是时间平均占用率或 SM 利用率。扫描另保存 `used_gpu_hours / 160`，用于交叉核验。

缺失分区、缺少对应节点观测的小时不补成零负载，也不跨缺失小时拼窗。所选窗口逐小时独立读取 `server_hourly`，核验原 20 台节点的集群、H20 型号、8 GPU 和 192 CPU 核。

候选排序预先固定为：窗口长度从长到短，再按任务数距 100 的距离从小到大，最后按窗口起点从早到晚。排序不读取执行时长，也不读取调度结果。

## 任务和时长代理

在选定窗口内按 `pod_id` 去重，保留原始 GPU/CPU 配对。对窗口内 GPU 或 CPU 请求变化（包括从正 GPU 变为零 GPU）的 Pod，明确列入排除清单。排除单节点无法承载或型号不一致的请求。保留下来的稳定任务仍须满足 50～150 个约束。

窗口选定以后，才读取 `asi_opensource_job_execution_summary`。匹配条件为原始 Pod ID、H20、完全相同的 GPU 请求，以及该 Pod 在本窗口实际出现过的宿主之一。多个兼容执行段取最长的正有限 `duration_hours`，保留原始执行表的零起始行号及匹配数量。CPU 请求来自小时表的真实配对，执行表不含 CPU 请求。

所有任务均标记 `duration_proxy=true`，即使只匹配到一行，也不声称识别到精确历史执行实例。缺少时长的任务列入独立清单，不补造时长；如余下任务不足 50 个，停止该组构造。

主实验采用统一缩放系数 `K=ceil(全体所选任务的最长原始秒数/90)`，服务时间为 `duration_hours×3600/K`。不截断、取整或给短任务设下限。另生成最长约 60 和 120 秒的统一单位缩放敏感性输入。

在每次都按同一目标ρ重新反推到达率时，统一改变K会同步缩放到达和服务时间，因此预期只改变秒数单位，不改变无量纲的排队/占用/碎片结果。这项检查验证尺度一致性，不能替代对时长代理误差或任务相对时长分布的敏感性分析。

## 到达过程和重复

对固定 N 个任务计算 `W=Σ(gpu_request×service_sec)`，令期望到达跨度 `T=W/(ρ×160)`，指数到达间隔均值 `Δ=T/(N−1)`，首任务在零秒到达。服务时间和 GPU/CPU 请求保持不变，排序与间隔使用独立随机流，种子为 42～71，共 30 组。

高负载窗口的主输入强度取 ρ=0.85，敏感性取 0.70/0.80/0.90；自然低负载窗口若存在，主值取 0.35，敏感性取 0.20/0.30/0.40。改变输入强度不改变源窗口的自然分类，也不被用于填补缺失类别。

实际指数间隔不重新归一化，因此实际末次到达时间有随机波动。输出同时记录期望与实际跨度、服务时间均值/P95/最大值、GPU 工作量及 CPU 工作量对应的输入强度。

`W/(ρ×160)` 校准的是输入强度。有限任务、空集群起步及最后排空使实际占用率不必等于 ρ，不能据此声称获得稳态高利用率。源窗口 CPU 分类包含 CPU-only Pod，而输入按提示只提取 GPU 正请求 Pod；不会暗中补 CPU 背景，仿真的 CPU 压力需单独核验。

## 仿真核验

FirstFit、BestFit、WorstFit 使用相同任务、相同到达时间、相同节点顺序与 backfill 队列。从 20 台空节点开始，没有预热、背景负载或原宿主绑定。BestFit 最小化放置后的 GPU/CPU 归一化剩余容量之和，WorstFit 最大化同一分数，平局均按节点顺序。

每轮排空到所有任务完成，检查无拒绝、无未完成、资源全部归还。核验实际 GPU 预留时间积分等于输入 GPU 工作量。

报告全程平均/P95 JCT、makespan、平均等待、吞吐量、GPU 预留率 AGU 和碎片时间占比。AGU 是已分配 GPU-equivalent 的时间平均比例，不是 SM 使用率。联合资源 AFR 定义为：有等待任务，其总空闲 GPU 与总空闲 CPU 均足够，但没有单个节点能共同承载该任务的时间占比；另外报告仅 GPU 维度的碎片指标。总 CPU 不足不被混入联合碎片。

保留全程指标，并辅以固定瞬态截点：末次到达时间的前 10%。资源积分从截点算到排空；JCT 次级指标只选提交时间不早于截点的任务，保留它们的完整等待与执行时间。各算法使用同一截点，不把这个有限样本区间称为稳态；makespan 始终按全程报告。

30 个种子的均值和双侧 Student-t 95% 置信区间逐项输出。算法差异按同种子配对后，再对差值计算区间。若缺少自然低负载窗口，不报告跨高低负载结论。

官方字段依据：[公开 schema](https://github.com/alibaba/clusterdata/blob/master/cluster-trace-gpu-v2026/docs/schema.md)。原始数据只读，扫描缓存和全部新交付位于本目录。

# S4 GPU 碎片整理实例

此实例来自真实 H20 需求，经受控重放置构造。筛选：通过；原因：全部固定条件满足。
完整规则、来源筛选偏差和复现环境见套件根目录 README.md。

- 随机种子 20261109；S1–S3 指数到达均值 10.0 秒。
- 100 台真实服务器，800 GPU；每台 8 H20 / 192 CPU 核。
- 初始 284 Pod，560 GPU（70%），5648 CPU 核；空闲卡数→机器数：{"0": 40, "2": 20, "4": 20, "6": 20}。
- 到达 120 个 Pod，GPU 卡数分布 {"1": 12, "2": 8, "4": 40, "8": 60}；到达结束 1605.30 秒。
- 到达 GPU 工作量 2272435.2000 卡秒；服务时长分位数 [min,Q1,median,Q3,max]：[1063.8301077421056, 1063.8301077421056, 4255.320430968422, 4255.320430968422, 4255.320430968422]。
- 初始残余时长分位数：[725.095492576298, 1361.3825090504627, 3081.9761222254474, 4748.602358859418, 6446.664141605267]。
- t=0 独立请求分类：{"direct": 60, "fragmentation": 60}。静态独立探测不是动态启动率。
- 8卡请求资源下界至少 1 次移动；已找到的最少移动数 1（启发式找到的上界，不是最优性证明）。
- 同步数决策空间审计：{"eight_gpu_found_plans": 94, "one_move_found_plans": 24, "one_move_cost_min_gpu_sec": 72.8, "one_move_cost_max_gpu_sec": 246.4, "one_move_target_hosts": 24}。不以额外多搬Pod造成的成本差异冒充选择难度。

## 文件与运行

servers.parquet、initial_pods.parquet、arrivals.parquet、config.json 是数据输入；运行时只向策略揭示当前资源、正在运行 Pod 的需求和已经到达的等待队列。完整 arrivals 由仿真器持有。
validation.json、screening.json、baselines/、evaluator_only/ 只给评测者。迁移见证只用于独立合法性验证，不能作为策略提示或输入。

```powershell
python verify_instance.py
python reproduce_instance.py --output 'D:\一般文件\benchmark任务\S4_reproduced'
```

verify_instance.py 使用根目录冻结源摘录独立重放八套基线事件；reproduce_instance.py 从冻结需求池、随机种子和构造器重建本实例，再比较全部输入和事件。完整原始数据复现见根目录 reproduce.py。
